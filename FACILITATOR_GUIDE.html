Session 1 - Meet your operator pipeline

Guide: Session 1 · Prompts 1.1, 1.2

"First, learn the pipeline you're on call for, and what its numbers say on a good day."

What we're doing

Asking CoCo to explain the operator's pipeline end to end and draw the lineage (Prompt 1.1), then asking Nova's semantic view the two questions operators ask most (Prompt 1.2). Nothing is changed.

What we're using

  • Tasks - TSK_BIFROST_MERGE simulates the Bifrost sync every minute.
  • Dynamic Tables - the REPORTING layer, incremental refresh, 1-minute lag.
  • Semantic view - the Gold layer Nova answers from, with a verified query.

Why it helps Gladstone

You can't monitor what you can't see. With one database per operator, every investigation starts by mapping that operator's Bronze, REPORTING and Gold objects - CoCo does it from live metadata in seconds.

Real-world angle

  • CS first response: before escalating to engineering, CS asks CoCo to map the operator's pipeline and which definition Nova used.
  • Onboarding: a new data engineer gets a plain-English map of any CUST_* database in minutes, instead of out-of-date docs.

Point out (don't explain yet): there are two different "active members" numbers. One counts members whose source status is ACTIVE; the verified query counts members who paid in the last 35 days. About 6% differ even on clean data. "Remember this number - it comes back in Session 3."

Stop & check (minute 4): hands up if you can name the 4 layers (Bronze, REPORTING, Gold/semantic view, Nova) and you've seen two numbers for active members. Ask one person to read theirs out.
If CoCo only gives one number: ask it to "show both definitions side by side" (it's in Prompt 1.2).
4-11

Session 2 - Put monitors on it

Guide: Session 2 · Prompts 2.1, 2.2

"Nothing is broken yet. Put monitors on your operator now."

What we're doing

Attaching data metric functions to the Bronze tables and a REPORTING Dynamic Table, on a 5-minute schedule, and turning each rule into an expectation that passes or fails (Prompt 2.1). Then a Bronze-to-REPORTING lag check, and evaluating everything right now (Prompt 2.2).

What we're using

  • System DMFs - DUPLICATE_COUNT, NEGATIVE_COUNT, FRESHNESS, ROW_COUNT, REFERENTIAL_INTEGRITY_COUNT.
  • Custom DMFs in a central DQ_COMMON schema - foreign-operator rows, active-but-left, reporting lag.
  • Expectations - pass/fail rules on any DMF; results land in SNOWFLAKE.LOCAL views.
  • Multi-table DMFs - compare a child with its parent, or Bronze with REPORTING.

Why it helps Gladstone

The checks run serverless, inside Snowflake, next to the data - no extra warehouse, no external tool. Defined once in DQ_COMMON, the same checks attach to every operator database.

Real-world angle

  • Replace homegrown checks scheduled on a monitoring warehouse with DMFs that have history, pass/fail and notifications built in.
  • Cross-tenant leak detection: FOREIGN_OPERATOR_ROWS on every operator database turns a GDPR incident into a 5-minute alert.
  • Bifrost sync SLAs: FRESHNESS and lag give CS and engineering one shared definition of "late".
  • Payments integrity: sign bugs and partial syncs caught before revenue dashboards move.

Talking point - expectations vs anomaly detection: anomaly detection on ROW_COUNT learns normal behaviour and needs about two weeks of history, so today it shows TRAINING_IN_PROGRESS - turn it on now so it works in two weeks. Expectations encode rules that must always hold and fail on the first bad run. Use both.

Stop & check (minute 10-11): everyone's 7 expectations pass on clean data; FRESHNESS under 180 s. Ask the room: "Tell me when you're green." Don't move on until most hands are up - the faults only make sense if the monitors are in place.
Stragglers: point them to the Behind? Run this box on Session 2 - it attaches everything in one go.

Session 3 - Diagnose a broken answer

Guide: Session 3 · Prompts 3.1, 3.2

What we're doing

Giving CoCo the complaint the way an operator would phrase it. It finds which check failed, the failing rows and the merge batch that caused it, whether the task and Dynamic Tables are healthy, which Nova metrics are affected - and writes a one-paragraph root cause (Prompt 3.1). Then it compares the two active-member definitions (Prompt 3.2).

What we're using

  • DQ results views - expectation status and results history in SNOWFLAKE.LOCAL.
  • SYSTEM$DATA_METRIC_SCAN - returns the exact rows that made a system DMF fail.
  • Task and Dynamic Table history - TASK_HISTORY, DYNAMIC_TABLE_REFRESH_HISTORY.
  • CoCo's data-quality skill - follows the same evidence trail an engineer would.

Why it helps Gladstone

This is the Customer Success escalation Gladstone handles by hand today. CoCo does it in minutes and shows its working - check, rows, batch, pipeline state, business impact.

Real-world angle

  • CS escalation in five minutes: the one-paragraph root cause is what goes back to the operator, with the batch id and the fix.
  • Bifrost incident review: batch-level evidence shows whether a replay or partial sync hit one operator or many.
  • Verified query drift: comparing a metric with its verified query catches semantic-layer drift no row-level check would.

Tell the room: scheduled checks run every 5 minutes - ask CoCo to evaluate the expectations now rather than wait.

Talking points as faults surface (use the answer key to pick who to call on):

  • Merge task stalled: FRESHNESS fails but Bronze-to-REPORTING lag stays 0. REPORTING isn't behind its source - the source stopped. That's why you need both checks.
  • Status drift: a semantic-layer problem. The gap between the two active-member numbers moved off ~5% (78 members) to ~20%. The agent answers from the verified query (paid in 35 days), the dashboard from status - two screens disagree.
  • Tenant leak: not just a data bug - it's a personal-data incident. Row access by operator would hide it immediately (Bonus B2).
  • Bifrost replay: the same batch applied twice - duplicates inflate active members. The batch id in _SYNC_META__MERGE_BATCH is the smoking gun.
Stop & check (minute 19-20): each person can say their fault in one sentence - which check, which batch, which Nova metric. Ask two or three people with different faults to read their root cause out. Then: "Compare with your neighbour - you each got a different one."
Stuck: check the answer key and nudge ("look at the merge batch history" / "is the task running?"). No failing checks at all: they may have joined late - the admin runs INJECT_FAULTS('<NAME>').
20-26

Session 4 - Contain and alert

Guide: Session 4 · Prompts 4.1, 4.2

"Now stop it spreading, and make sure the next one emails you instead of the operator calling."

Role check first: "Confirm CoCo says your current role is DQ_LAB_<NAME>." The circuit-breaker task is owned by whoever creates it - a task created under someone's usual role can't suspend their operator's Dynamic Tables.

What we're doing

Building a circuit-breaker task that runs every minute: if any Bronze expectation is failing it suspends the REPORTING Dynamic Tables, otherwise resumes them, and records what it did (Prompt 4.1). Then fixing the fault, watching the breaker close, and choosing which checks email (Prompt 4.2).

What we're using

  • Tasks with a Snowflake Scripting body and SYSTEM$SET_RETURN_VALUE - the breaker's state shows in task history.
  • Dynamic Table suspend / resume - pause REPORTING while Bronze is failing.
  • DQ notifications - enabled once per database; each check toggled on or off; email or webhook.

Why it helps Gladstone

Detection alone still lets Nova serve a wrong number. Pausing REPORTING stops further bad batches reaching Nova - stale beats wrong. Notifying only on the critical checks avoids alert fatigue across hundreds of operators.

Real-world angle

  • Protect Nova before month-end: during a bad sync, Nova keeps answering from yesterday's good data while finance reports run.
  • Slack or Teams for on-call: swap the email integration for a webhook so tenant-leak alerts page the right channel.
  • Per-tier alert policies: enterprise operators get notifications on every invariant; smaller ones on the critical two.

Honest caveat to mention: with 5-minute checks and 1-minute REPORTING, the first bad batch can already be in before the breaker opens. Checks triggered on change (instead of a schedule) close that gap in production.

Stop & check (minute 25-26): the breaker's run history shows OPEN, then CLOSED: Bronze clean after the fix, and the REPORTING__* Dynamic Tables are active again. Notifications on only for no_other_operator_rows and no_duplicate_members.
Breaker never opens: task created under the wrong role, or not resumed. Breaker stays open: the fix didn't clear the check - re-evaluate expectations. Fixes per fault are in the table below (and on the Session 4 page).

-- ---------------------------------------------------------------------------
-- Session 4  Contain + alert
-- >>> ROLE CHECK: the circuit-breaker task is owned by whichever role creates it.
-- >>> Confirm SELECT CURRENT_ROLE() = DQ_LAB_OPERATOR01 before CREATE TASK.
-- ---------------------------------------------------------------------------
-- Circuit breaker: suspend REPORTING while any Bronze invariant is violated; resume when clean.
CREATE OR REPLACE TASK TSK_DQ_CIRCUIT_BREAKER
  WAREHOUSE = DQ_LAB_WH SCHEDULE = '1 MINUTE'
AS
EXECUTE IMMEDIATE $$
DECLARE
  bad NUMBER;
  msg VARCHAR;
BEGIN
  SELECT COUNT(*) INTO :bad FROM (
    SELECT expectation_violated
    FROM SNOWFLAKE.LOCAL.DATA_QUALITY_MONITORING_EXPECTATION_STATUS
    WHERE table_database = 'GLADSTONE_DQ_LAB' AND table_schema = 'CUST_OPERATOR01'
      AND table_name IN ('MEMBERS__MEMBER', 'SYSTEM__PAYMENT', 'SYSTEM__ATTENDANCE')
    QUALIFY ROW_NUMBER() OVER (PARTITION BY table_name, expectation_name ORDER BY measurement_time DESC) = 1)
  WHERE expectation_violated;
  IF (bad > 0) THEN
    ALTER DYNAMIC TABLE GLADSTONE_DQ_LAB.CUST_OPERATOR01.REPORTING__ACTIVE_MEMBERS SUSPEND;
    ALTER DYNAMIC TABLE GLADSTONE_DQ_LAB.CUST_OPERATOR01.REPORTING__DAILY_REVENUE SUSPEND;
    -- SYSTEM$SET_RETURN_VALUE needs a plain variable or literal, not an expression
    msg := 'OPEN: ' || :bad || ' failing Bronze check(s) - REPORTING refresh paused';
    CALL SYSTEM$SET_RETURN_VALUE(:msg);
    RETURN 'OPEN';
